# dsh-model-orchestrator — 模型调度（两级）

先选**模型**，再选这个模型所在的**渠道**；失败时先换渠道、再换模型。
输入框下方实时显示当前模型、渠道健康、今日用量与自动切换记录。
**新会话的第一条消息就按调度结果调用模型**（不再先跑选择器里的那个），新会话首屏也有同一份状态与开关。

装在 DSH 里就是一个 bundle：一个 Host 半身（路由决策）+ 一个浏览器半身（状态条与详情面板）。

> **配合 [dsh-our-free-model](https://github.com/Ebony-Vinyl/dsh-our-free-model)（OFM）使用——推荐一起装，但不是依赖。**
> OFM 把免费模型接进来，本插件在这些车道之间做调度。两者零代码依赖，
> 只有 OFM 写在本机的状态文件被当作额外信号读进来。**这是单向适配、非官方**：
> 我们读它的文件，它不需要知道本插件的存在。详见 [与 dsh-our-free-model 的关系](#与-dsh-our-free-model-的关系)。

## 与 dsh-our-free-model 的关系

**本插件与 [dsh-our-free-model](https://github.com/Ebony-Vinyl/dsh-our-free-model)（OFM）配合使用。** 先说清楚关系的性质：这是**单向适配，不是合作，也不是官方关联**——OFM 的作者没有参与本插件、也没有为它背书；本插件只按 OFM 当前写盘的格式去读它留下的状态文件，不对 OFM 提任何适配要求，也不向它的仓库提交改动。分工是这样的：

- **OFM 负责「把免费模型接进来，并记录渠道状态」**——免登录、免注册、免 API Key，
  把一批前沿模型注册成 `our-free-model` / `our-free-model-region` 两条 provider 车道；
  并在本机维护一份渠道账本（`$DSH_HOME/channel-pack/`，记录账号、每账号每模型的限流解禁时间、
  逐渠道首字与今日 token，以及免费车道的可用性探测结果）。
- **本插件负责「在这些车道之间做调度」**——选哪个模型（智力/速度/成本/用量打分）、走哪条渠道
  （实时健康、限流、首字、粘滞）、失败了先换渠道还是换模型、锁定一个模型时怎么在它的渠道间切换。
  它**不产生模型**，只决定请求走哪条已经存在的路。

两者**没有代码依赖，也没有互相 import**（`package.json` 里没有 `dependencies`），
模型清单来自内核的 LLM 注册表（`llm.listProviders/listModels/resolveModelInfo`），**不硬编码任何渠道**。

| 你装了什么 | 得到什么 |
| --- | --- |
| 只装 OFM | 免费模型可用；走哪条渠道由 OFM 自己决定，本插件不参与 |
| 只装本插件 | 任何 DSH provider 都能正常路由；少了 OFM 那层渠道旁证，改用本插件自己观测的流量账本 |
| **两个都装（推荐）** | 免费模型 + 两级调度：渠道健康排序、失败先换渠道再换模型、偏好锁定、状态条全部生效，且冷却与限流以 OFM 账号池的真实解禁时间为准 |

### OFM 提供哪些信号（可选）

OFM 往本机写四个 JSON，本插件**只读不写**：

| 文件 | 由谁写 | 不装 OFM 时 |
| --- | --- | --- |
| `$DSH_HOME/our-free-model/availability.json` | OFM | 免费车道的可用/不可用判定缺失，该渠道按「未知」处理 |
| `$DSH_HOME/our-free-model/stats.json` | OFM | 免费车道的今日用量缺失，用量项按 0 计 |
| `$DSH_HOME/channel-pack/state.json` | OFM（内嵌 channel pack） | 拿不到每账号每模型的限流解禁时间，冷却判定改用本插件自己观测到的失败 |
| `$DSH_HOME/channel-pack/token-ledger.json` | OFM | 少了第二优先的延迟证据，延迟只认本插件实测和报告值 |

读不到文件、格式不认、provider 不认识，一律降级成「没有信号」——`signal()` 返回 `available: null`（未知），
不是 `false`（不可用），所以未知不会被当成坏渠道排掉。
想彻底关掉这两个来源：配置里 `channelData: false` 和 `freeModelData: false`。

这四个文件是 OFM 的内部实现细节，没有版本承诺，也没有为第三方准备的契约。本插件**单向跟随**：
按它现在写盘的格式读，格式变了就退回「没有信号」，不要求 OFM 为本插件做任何改动。

**证据**：集成测试 `tools/integration.mjs` 把 `DSH_HOME` 指向一个空临时目录
（既没有 `our-free-model/` 也没有 `channel-pack/`），在这个前提下加载真实的 Host 半身、
跑通路由、失败换渠道、偏好模式与暂停恢复——52 项全过。

## 安装

需要一个已经装好的 DSH（Desktop 或 `dsh web`）。

```bash
# 1) 把仓库放到任意目录，然后作为一个本地 link 依赖装进你的 DSH profile
cd ~/.dsh/profiles/web
pnpm add link:/absolute/path/to/dsh-model-orchestrator
```

```bash
# 2) 把 dsh-model-orchestrator 加进 ~/.dsh/profiles/web/package.json 的
#    dsh.profile.bundles 数组（漏了这一步插件不会被加载）
# 3) 重启一次 DSH Desktop（或 dsh web）
```

Host 半身只在启动时加载一次，浏览器半身（状态条/详情面板）由 HMR 或刷新页面加载。

验证：输入框下方出现模型状态条；`/route status` 能列出模型组；
`model_orchestrator {"action":"status"}` 的 `catalog.total` > 0。

## 它解决什么

你手上有十几条免费/低价渠道，同一个模型（比如 `glm-5.3`）往往在 4~6 条渠道上都有。
真正要回答的问题不是「哪个模型分数最高」，而是：

1. **现在该用哪个模型？** —— 由报告里的智力分、实测速度、成本和你的偏好共同决定。
2. **这个模型该走哪条渠道？** —— 由渠道的实时健康、限流、额度和实测首字决定。
3. **渠道挂了怎么办？** —— 先换同模型的其它渠道；只有整个模型的渠道都用不了，才换模型。
4. **我只想用某个模型。** —— 打开**偏好模式**：只调用该模型，自动在它的渠道间切换；全部渠道不可用时暂停偏好、改用备用模式并提醒你。

旧版把「模型」和「渠道」压成一个分数：每次失败都重新给所有 `provider/model` 排序，
于是可能在 `glm-5.3` 的另一条渠道还活着的时候，换到一个更弱的模型上。
这一版把两层分开，并把「用户明确选的模型」放到最高优先级。

## 优先级是怎么算的（可以逐项复述）

**模型层**（选哪个模型的权重）：

| 项 | 含义 | 数据来源 |
| --- | --- | --- |
| quality | 智力分 / 46，按可信度向中性收缩 | 测速报告（先验） |
| speed | `1/(1+首字/10s)` | 本机实测优先 → 渠道账本 → 报告逐车道 |
| health | `1/(1+0.8×衰减失败数)` | 本机流量账本 |
| cost | `1/(1+家族消耗×车道倍率)` | 报告标签 + 模型名里的 `x0.2` 倍率 |
| usage | `1/(1+今日 token/2M)` | 渠道账本今日用量 |

四档策略只是重新分配这些权重（每档权重和为 1）：

- **quality**：智力 0.58，速度/健康/成本/用量各占少量；
- **balanced**（默认）：智力 0.46，速度 0.18，健康 0.14，成本 0.14，用量 0.08；
- **economy**：成本 0.30，智力 0.34；
- **speed**：速度 0.34，智力 0.34。

**渠道层**（同一个模型内选哪条渠道）：同样的五项，但 quality 相同（同模型），
真正起作用的是健康、首字、倍率、今日用量，以及「是否正持有本会话的 prompt 缓存」。

五项都是**历史**读数。第六项是唯一看当下的：**此刻这条渠道上有几个调用正在飞**
（并发分散，见后文）—— 它是扣分项，不是权重，所以五项仍然和为 1，排名依旧可审计。

**粘滞**：当前模型/渠道领先不到切换阈值时不换；切换阈值随任务复杂度收紧或放宽。
用户刚在选择器里手动选过的模型，切换阈值翻倍（默认 30 分钟内）。

**失败处理顺序**：

1. 记录到**实际失败的那条 `provider/model`**（用 `agent/request` 的最终配置，而不是可能滞后的请求头）；
   同一车道、同一失败类型在 `failureBurstWindowMs`（默认 5 秒）内的多次上报只算一次事件 ——
   并发会话撞同一堵墙时不会把冷却翻成好几倍；
2. 先在同模型的其它渠道里重试（同一步内 `{kind:'retry'}`，调用方看不见）；
3. 整个模型都没有可用渠道时，才按策略换模型；
4. 偏好模式下第 3 步会触发「偏好暂停」：改用备用模式并通知，渠道恢复后自动恢复偏好。

**两种「不是我们的错、但也不能一直忍」的情况**（LOCAL PATCH 2026-10-18）：

- **渠道安全审核拦截**（如腾讯 CodeBuddy/WorkBuddy 回 `HTTP 400 请求被拦截，请重新发送 request illegal`）。
  这类 400 会被识别成 `safety` 判定：该渠道对**这个模型**冷却 30 分钟，同渠道的其它模型不受影响，
  本次请求立刻换渠道重试。以前它被当作 `INVALID_REQUEST`（「我们的请求写错了」），于是既不冷却也不换渠道，
  连续两个回合都撞同一堵墙。
- **连续被同一个渠道拒绝**（任意 400）。单次 `INVALID_REQUEST` 仍然**不动路由**（渠道无罪），
  但同一渠道 `requestRepeatThreshold`（默认 2）次、在 `requestRepeatWindowMs`（默认 10 分钟）内接连拒绝时，
  该模型被暂停 `requestRepeatBlockMs`（默认 30 分钟）并立刻换渠道。收到一次成功响应就清零。

## 并发分散与失败突发去重（LOCAL PATCH 2026-10-26）

### 问题：五项的分数全是历史

原来的打分只有五个读数：智力、速度、健康、成本、用量 —— **全部来自过去**。历史分不清
「两个会话同时开」和「一个会话问两次」，所以 N 个会话同时发请求时，每个会话都算出同一条
渠道最优，然后一起压上去。免费渠道的额度是按 key（常常还按 IP）算的，压上去并不会更快：
一份配额被切成 N 份，接着换来一串 429，而 429 的冷却是**渠道级**的 —— 一个会话的限流会把
同一条渠道上所有会话一起停掉。

### 修法一：把「此刻在飞几个」加进打分

`src/inflight.js` 记录每条 `provider/model` 与每个 provider 当前打开的调用数（`llm/stream` 是
所有模型调用的唯一入口，租约在那里取、在 `finally` 里释放，所以成功/抛错/取消/消费者提前
break 都会归还；超过 `concurrencyStaleMs` 的租约自动失效，不会因为某个流没关掉就永久压死一条渠道）。

打分时按它扣分，**扣分而不是排除**：忙的车道只是分数更低，仍然可路由 —— 一条永远不被选中的
渠道永远没有机会证明它恢复了。

| 读数 | 含义 | 权重 |
| --- | --- | --- |
| 本路由在飞数 | 这条 `provider/model` 上有几个调用正在跑 | 主项 |
| 同渠道在飞数 | 这个 provider 上（其它模型）还有几个调用在跑 | 半权重 |

实测（两条各项完全相同的车道）：空闲时两者同为 0.824；A 会话占住 buddy 后，buddy 掉到
0.734，第二个会话选 raccoon。扣分上限 0.18 大于 `laneSwitchMargin`(0.05) 与 `anchorBonus`(0.04)，
所以「知道它忙」一定换得动；又小于 balanced 的一整档智力权重（0.46），所以真的更好的模型仍然赢。

### 修法二：同一堵墙只记一次

并发的会话撞到**同一堵墙**时各报一次失败，而旧实现每报一次就 `strikes += 1`，冷却时间按
`2^(strikes-1)` 翻倍 —— 一次上游事件，五个会话，五倍冷却。

现在的规则很窄：**同一条路由 + 同一种失败类型 + `failureBurstWindowMs`(默认 5 秒) 之内**算一次事件。
第二次起只更新诊断信息，不加 strike、也不把冷却截止时间往后滑（往后滑正是「突发变长期」的机制）。
不同类型（429 之后 401 = key 中途失效）仍然各记一次，不同路由更是各记各的。

实测：五个并发 429 的冷却序列从 `20s,40s,80s,160s,300s` 变成 `20s,19.5s,19s,18.5s,18s`
（后四个报的是**剩余**时间，所以只会变短）。

面板与 `route_status` 的返回里新增 `concurrency`：当前每条路由/每条渠道各有多少个在飞调用，
「为什么选了第二名」从此有可见的答案。

## 渠道互借（2026-10-29，v2.6.0）

### 它解决什么

本机跑着两套独立 DSH（A 主实例、B 独立实例），两边的**账号额度完全独立**。实际用起来
总是一边先烧穿：A 的免费车道限流了，B 那边还闲着。以前只能人肉去 B 里干活。

打开这个开关后，**额度充裕的一端可以把车道借给对侧用**：请求真的在对侧进程里发出去，
消耗的是对侧的账号额度，本机的会话不受影响。

### 为什么必须走线路级中继

两端注册的 provider 列表几乎一样（同一个 channel-pack），真正不同的是账号与额度。
所以「借对侧的渠道」不是复制一份配置能成立的 —— 请求必须在对侧进程里发出。
于是实现是：

```
借用方 (B)                                   出借方 (A)
  peer 适配器  ──── POST /peershare/v1/stream ────▶  ctx.llm.stream()
  (一条普通 provider)                                (A 自己的车道)
       ▲                                                  │
       └────────── NDJSON: {type:'chunk',chunk} ──────────┘
```

### 线上协议不是 OpenAI wire

两端是同一个插件版本，可以直接收发 harness 自己的 `GenerateOptions` / `StreamChunk`
（都可无损 JSON 化）。走 OpenAI wire 要多写一遍 messages / tool_calls / SSE 的双向翻译，
多出来的每一行都是「翻译错了但看起来通了」的风险。协议带 `protocol` 字段，不匹配就明确
拒绝（`PROTOCOL_MISMATCH`），不做兼容猜测。

### 配置

```yaml
- id: model-orchestrator
  config:
    peerShare:
      enabled: true
      role: both            # off | both | lend | borrow
      label: 'A'            # 面板上显示的对端名字
      host: 127.0.0.1       # 出借端点监听地址（默认只绑回环；跨机用才填局域网 IP 或 0.0.0.0）
      port: 18326
      token: ''             # 空 = 用 $DSH_HOME/model-orchestrator/peer-token
      allowProviders: []    # 只借出这些 provider（空 = 全部）
      denyProviders: []     # 永不借出
      peerUrl: 'http://192.168.1.20:18327'   # 借用方：对侧地址
      peerToken: '<对侧的 token>'
      peerProvider: peer    # 借用车道在本机的 provider 名
      borrowWhen: exhausted # exhausted（本机全灭才借）| always（一直参与打分）
```

面板：设置页有一个「渠道互借」开关 + 角色 + 借用时机；命令行：

```
/route peer              # 看状态：出借端点、可借车道数、借用方拿到几条对侧模型
/route peer on           # 打开
/route peer off          # 关闭（端点立即停止监听）
/route peer lend         # 只出借
/route peer borrow       # 只借用
```

模型侧：`model_orchestrator action=peer`，或 `action=set` 带 `peerShare` 字段。

### 三条必须知道的语义

1. **`borrowWhen: exhausted` 是默认，不是保守**。互借是兜底，不是常态：本机还有任何合格
   车道时借用车道不进入打分。否则会用对侧的账号替本机烧钱，而且对侧一断线，本机明明
   有可用车道却先撞墙。要两端按打分自然分摊额度，才改成 `always`。
2. **图片不跨实例**。图片块引用的是本机附件 id，对侧读不到。适配器因此不声明 image
   模态（路由层不会把带图请求派过来），真收到图片块时明确报 `UNSUPPORTED_CONTENT`，
   而不是让模型「看不到图却照答」。
3. **只借车道，不借权限**。借用方能调的只有出借方**当前可路由且未 denied** 的
   provider/model；`allowProviders` / `denyProviders` 可以再收窄。开了互借绝不会多出
   一条出借方自己没有的渠道。

### 安全边界

- token 落 `$DSH_HOME/model-orchestrator/peer-token`（首次开启自动生成 32 字节），
  比较走 `timingSafeEqual`，长度不同直接 false；
- **回环守卫**：请求带 `x-peershare-hop` 头，或 provider 名等于本机的借用车道，直接 508。
  这条踩过：借用方是链路**起点**，不该带 hop 头（带了就被自己的守卫拒绝）；
- 出借端点**默认只绑 `127.0.0.1`**（2026-10-29 改）：拿到 token 就能花对侧的额度，
  一个默认开在局域网的端口等于把额度暴露给同网段任何一台机器。要跨机用就显式填局域网
  地址或 `0.0.0.0`，并自己确认防火墙只放行对侧那一端。

4. **借来的车道是聚合体，判决只能到模型级（v2.6.1）**。`peer` 这一个 provider 下面挂的是
   对侧的**全部**模型（实测 B 侧 600 条）。所以「这条车道不能服务」在这里等于「对侧全灭」，
   而那从来不是一次失败能证明的事。实测事故：借用方调 `xiaomi/mimo-v2.6-pro` 拿到 cline 的
   402（文案是「改用其它 **provider**」），分类器只认「其它**模型**」→ 判成车道级 → 10 条
   活着的借入车道被一起停到午夜。现在聚合车道上的任何 `scope: 'lane'` 判决在记账前降为
   `scope: 'model'`，reason 前缀 `〔聚合车道：仅本模型〕`；磁盘上旧代码泼下来的车道级停车
   在下次加载时清掉。**真实渠道的行为一个字节没变**（同一条 402 在 cline 上仍是车道级）。
   判据来源只认 `peerShare.peerProvider`，关掉互借后旧记录不再被当聚合体。

5. **探活默认不探借入车道**（`probeBorrowed: false`）。定时巡检要回答的是「本机车道会不会
   静默死亡」，拿对侧的账号额度给本机做体检是另一回事，量级还差两个数量级。

### 自检

## 偏好模式

面板里点「偏好」，或在 `/route` 里：

```
/route prefer glm-5.3          # 只调用 glm-5.3，自动在它的渠道间切换
/route prefer glm-5.3 buddy    # 限定只走 buddy 这一条渠道（该渠道挂了就算偏好不可用）
/route unprefer                # 回到自动
```

规则：

- **同一个模型，换渠道不换模型。** 渠道限流/额度耗尽/不可用时，优先在同模型的其它渠道重试。
- **只在本步不满足时临时改选。** 如果这次请求需要图片、而偏好模型不支持视觉，或者上下文超过它的窗口，
  这一步会临时用别的模型，但**不会**暂停偏好模式（下一次请求仍回到偏好模型）。
- **所有渠道都不可用才暂停。** 判定标准是渠道级：冷却、被屏蔽、渠道面板关闭、免费车道探测不可用。
  暂停时：状态条变黄、面板显示原因与倒计时、桌面端弹通知；默认在渠道恢复后自动恢复并再通知一次。
- **选择器跟着走。** 路由切换会写入内核的 `model/selection`，所以浏览器里的模型选择器、会话日志、
  模型收到的「模型已变更」提示、面板显示的模型是同一个。
  在偏好模式下从选择器里改选模型，会把偏好模型一起改掉（可在配置里关闭）。

## 判据的三条修正（2026-11-05，v2.7.0）

这三条都来自 2026-11-04 的四次线上排查，每一条都对应一次可复现的事故。

### 1. 线路问题优先于凭据问题：断网不再被「凭据」二字判成账号失效

事故：WiFi 断 3 分钟，探活把 `Loomy 凭据探测网络失败：fetch failed` 原样交给分类器，
`AUTH_TEXT` 里的「凭据」命中——那是这条**链路的显示名**，不是判决——整条车道被判 `auth`、
停 30 分钟，网络恢复后仍锁在原地。同一段断网在另一实例只吃 30 秒模型级冷却。

改法：分类器在凭据分支**之前**先认网络证据（`fetch failed` / `ECONNREFUSED` / `getaddrinfo` /
`socket hang up` / 连接重置 / 证书 …），命中即为 `transient` + 模型级 + 30 秒量级；
真凭据失效（`invalid api key` / 401）不带网络词，判决一个字节不变。

同时补上第二层：**探活不是证据**。探活是插件自己排的 8 token 心跳，它的失败一律模型级，
冷却不超过 `transient` 的两倍，并在 `reason` 里标出 `〔探活〕`。真正的额度耗尽/凭据失效会在
用户的下一次真实请求上再次出现，那时再按重判决处理。

### 2. 端点不可达 = 整片下线（互借第二个方向）

v2.6.1 把聚合车道（互借）上的车道级判决降为模型级，修的是「一个借入模型 402 把对侧几百条
车道一起停到午夜」。但连接层失败根本不是在说某个模型：`ECONNREFUSED` 说的是**这个端口上没有监听**，
而互借的几百条借入车道共用同一个 base URL。旧方向下，路由会在同一个死端口上把 3 次换道预算烧光，
整轮 `agent turn failed`（实测 2026-11-04 00:09，三连）。

改法：聚合 provider 上 `connectivity` 类的判决**升回车道级**并标 `endpointDown`，同一端点的所有借入
车道一起退出候选；`clearEndpointDown(provider)` 由清单拉取成功显式解除（只在一次成功调用上解除是不够的
——整片被跳过的端点永远不会有人去调用它）。非连接类的判决（402/额度/地区/凭据）照旧降为模型级。

配套两条：

- **清单失效即不可用**：借用适配器区分「端点不可达」与「对侧拒绝请求」，前者把 `usable` 置 false，
  路由层据此整片跳过借入车道（旧代码只记 `modelsError`、留着旧清单，于是按陈旧清单把请求派给一个
  已经不存在的端口）。
- **借入车道不原地重试传输层失败**：`providerRetryPolicy` 从默认（5 次、约 15 秒、含 `TRANSPORT`）
  收紧为 1 次且不含 `TRANSPORT`——同一个死端点原地重试只是同一堵墙撞 5 次，换道才是出路。

### 3. 偏好暂停自愈，不再粘在会话里

`preferenceSuspended` 是会话级内存态，旧代码只在「该会话下一次路由」时重新评估。断网时恰好空闲的
会话，网络恢复后仍一直显示「已暂停 / 自动」——用户看到的是「有的会话退出了偏好模式、有的没有」。
现在面板读取与每次 step 组装都会走一遍实时复核（复用 `selectRoute` 的 prefer 分支，保证「面板说能用」
与「路由真的会用」是同一件事）；车道仍然坏着时不会自愈。

### 4. 换道代价随目标车道价格缩放

「额度不是变少了，是被最贵的那条车道吃干的」：缓存重读惩罚（`cacheSwitchPenalty`）的物理含义是
「换道后整个上下文按未命中缓存重新计费」，那它就必须乘上目标车道的价格。固定 0.35 的实测后果是——
x0.06 与 x2.0 车道的效用差只有 0.137，而换道要付 0.35，净差 **-0.213**，迁移在结构上不可能发生。
改为按 `burn / cacheRebillRefBurn`（默认 0.45，可配）缩放并夹在 [0.1, 1]：便宜车道的重读惩罚缩到零头，
基准价格的车道照旧付满额。

## 渠道异名与身份指纹（2026-11-13，v2.8.0）

免费与聚合渠道大量使用不透明 id。两层机制把它们映射回真实家族，**第二层是这一版新加的**：

| 层 | 位置 | 解决什么 |
| --- | --- | --- |
| 模式折叠 | `src/families.js` | 渠道命名空间（`z-ai/`）、前后缀（`sn-`、`-1017`、`:free`）、虚线版本号；置信度 0.65–0.95 |
| **已验证别名表** | 报告的 **第九节** → `canonical` | 模式猜不出来的名字，逐条给出证据后写死；置信度 1.0 |

别名表的读法：`| 别名 id | 家族 | 置信度 | 依据 |`。它由 `tools/_merge-priority.mjs` 从实盘
清单差集（`_catalog-diff.json`，只取 **observed** 层、置信度 ≥0.6）灌入报告第九节，再由
`tools/build-data.mjs` 折回 `canonical`。**构建号、区域标记、`:free`、`@preset/` 一律不进别名表** ——
那些 id 本来就该走折叠路径（`source: 'folded'`），写进别名表会把一次"有据可查的折叠"降级成"静默命中"。

### 身份指纹：三条实测结论（`tools/_fingerprint.mjs`，2026-11-13）

对着 16 条车道发过 59 次探针（未消耗任何计费渠道），结论**与方法直觉相反**：

1. **自述不可信。** 同一个 id、同一条 prompt 跑两次，答案互斥（一次"DeepSeek/深度求索"，
   一次"GPT-4/OpenAI"）。自述只证明"渠道想让这个名字看起来像什么"。
2. **`usage` 帧才是硬证据。** 同一段 125 字符样本，不同渠道回来的 `inputTokens` 是 52/61/77/78。
   在同一渠道内建基线表后，**改名但计数不变 = 后端没换**——这正是 `sn-`、`-1017`、`*_latest`
   这类改名的判据，也说明为什么报告第九节只收"改名"不"改模型"的条目。
3. **分档要用陷阱题。** "恰好 5 个字"这类指令跟随陷阱能分档（MiniMax-M3.1-Flash 守住，
   GLM / spark / deepseek 全给 7 字）；`9.11 vs 9.9` 本次全部答 9.9，没有区分力，只能当基线。

单点复现：`node tools/_fingerprint.mjs --provider loomy --model GLM-5.3-Flash`；
批量：`--batch _fp/batch-a.json`。原始证据 `_fp/*-raw.ndjson`，请求账目与阻塞清单见
`_fingerprint-report.md`。

## 失败分类、连败升级与偏好冲突（2026-11-14，v2.9.0）

这一版全部来自 2026-11-12～11-14 的实盘日志（76 个会话、262 次模型重试、3 次整轮以错误结束）。
四类问题都满足同一个形式：**账本里记着的信息，决策时没有用上**。

### 1. 「没登录」不是 30 分钟的故障，是配置状态（12 小时停车）

现场：workbuddy 车道被判 `auth`、停 30 分钟；到期立刻被重新选中，然后**第一步就以
`未配置凭据，请先登录` 结束整轮**（`turn/end kind:error`，三天内 2 次）。
等 30 分钟不会让任何人去点那个登录框，它只会让同一个错误每小时重演一次。

新判决：message 命中「未配置凭据 / 请先登录 / not configured / please log in」时按
`COOLDOWN.credential`（12 小时）停车，并在 reason 里写清楚要做什么。真凭据失效
（`invalid api key`、401）不受影响，仍是 30 分钟 + 连败升级。

### 2. 订阅/套餐型失败有了自己的判决（`KIND.PLAN`，6 小时）

三种文案以前全都掉进 30 秒的 transient 默认分支，于是每一轮都在撞同一堵墙：

| 渠道 | 原文 | 旧判决 | 新判决 |
| --- | --- | --- | --- |
| qoder / qodercn | `{"pricingUrl":"…"} (112/model_error)` | transient 30s | `plan` 6h |
| cline | `Error 403: the user is not subscribed to required model plan` | auth 30min（凭据是好的！） | `plan` 6h |

三天内这两类合计重试 55 次。面板状态与 `/route` 都直接写「需订阅/套餐」。

### 3. 同一条线连着犯同一种病，冷却逐级升级

各类冷却原本都是常数（auth 固定 30 分钟、transient 封顶 5 分钟），而 strikes 按 3 小时半衰期
衰减——**每半小时失败一次的车道，每次失败时衰减后的 strikes 都贴近 0**，冷却永远停在初始值。
日志里 trae/qoder 的 `transport error: fetch failed` 分别被选中 48/39 次，就是这么来的。

现在：同一条路线、同一种判决、30 分钟内再次出现 → 冷却 ×2，最多 ×8，并按判决类型封顶
（transient 30 分钟、auth 6 小时、quota 到本地午夜、plan 6 小时）。**一次成功调用即清零**，
生病过的车道可以自己翻身。关掉：`sameKindEscalation=false`。

### 4. 陈旧但真实的延迟读数不再被当成「未知」

our-free-model 的 `deepseek-ai/deepseek-v4.1-flash` 实测首字 **304 秒**（免费池排队），
但这条读数超过 2 小时后被判过期，掉进 `source: 'none'` 拿到中性的速度分 0.5 ——
"我们不知道它多慢"与"我们知道它慢得不能用"被当成了同一件事。同期
`upstream stream idle past its deadline` 出现 14 次。

现在过期读数仍参与打分（`source: 'stale'`）；一次成功调用刷新 EWMA 即回到 `live`。
想回到旧行为：`staleLatencyMode=neutral`。

### 5. 偏好模式与用户自己的 deny 列表冲突时会点名

2026-11-13 的事故：偏好模型 deepseek-v4.1-flash 被判「全灭」，用户改用自动模式；
而他**手动**选同一条 OFM 免费 flash 车道时能用——因为手动选择不经过 deny。
真正的差别是那两条健康车道写在用户自己的 `deny` 里：

```
deny: ["workbuddy/deepseek-v4.1-flash-sg",
       "our-free-model/opencode/deepseek-v4.1-flash-free",
       "our-free-model/deepseek-v4.1-flash-free"]
```

被 deny 挡住的渠道**不会随时间恢复**，而旧文案把它们和"冷却中"混成同一句
「全部 16 条渠道不可用」。现在：

- `status` / 面板的 `preference.group.conflicts` 列出被 deny 挡住的每一条及其 deny 原文；
- 暂停通知改口径：「可用渠道已用尽，但其中 2 条是被你自己的屏蔽列表挡住的（…），
  删除对应 deny 项可立即恢复」；
- `explainExhausted` 在 reason 里带上同样的下一步。

### 6. 同一家族在一个 step 里只烧一次换道预算

偏好家族 `deepseek-v4.1-flash` 挂 16 条同名车道，事故当时其中 13 条不可用
（2 条被策略排除、2 条未登录、4 条未订阅、1 条额度到中午、1 条被用户屏蔽、1 条安全拦截）。
失败恢复的既有规则是"先在同一家族换个渠道"，于是 **3 次 `maxSwitchesPerStep` 全花在同一个
家族的兄弟车道上**，整轮以最后一个错误结束，连"换一个模型"都没走到。

现在：同一家族在同一个 step 内失败两次后，`recover()` 把它放进 `excludeFamilies`，
本步骤改试其它家族；**只有当过滤后还有别的家族可用时才生效**（全灭时自动让路，见
`evaluate` 的 survivor 守卫）。偏好模式下这只降级**本次请求**，偏好本身不退出。

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `sameKindEscalation` | `true` | 同类连败时逐级延长冷却 |
| `staleLatencyMode` | `'penalize'` | 过期延迟读数仍参与打分（`neutral` = 旧行为） |

### 回归用例

`node tools/smoke.mjs` 的 `[15] 2026-11-14 事故回归` 一节逐条锁住上面六件事

## 失败恢复三件套：不再「弹运行失败、等人重试」（2026-11-16，v2.10.0）

这一版只针对一句话：「有时候第一轮就弹运行失败，失败后还得用户重试；有时候跑一段时间后
失败，也得用户重置」。证据来自 11-10～11-16 的 **134 个会话 / 295 个回合**：

| 观测 | 数值 |
| --- | --- |
| turn/end 以 error 收场 | **38 / 295**（12.9%） |
| 发生在新会话**第一轮**的 error | **11 / 125**（9%） |
| 最后一个步骤里失败次数 ≥10 的 error 回合 | **13 / 38** |
| 单个步骤内的极端失败次数 | 22 次（b449551d，仅 3 个 provider） |

三个根因，三个补丁。

### 1. 内核的同车道重试与调度器的换道在乘法

@deepseek-ai/dsh-llm-retry 与这个插件都挂在 agent/request-error 瀑布上，**谁先注册谁先
说话**。llm-retry 对同一 provider 的 TRANSPORT / TIMEOUT / SERVER / RATE_LIMIT /
EMPTY_RESPONSE 有独立的 5 次重试（0.5s→10s 退避）；它先跑，一次失败就被它吞掉 5 次，
调度器要到第 6 次才看得见。于是「同一条死车道撞 15~22 次」与「预算只够 3 次换道」同时成立。

现在 ownRetryBudget: true（默认）让调度器 prepend 到瀑布最前面：车道级故障立刻换道并
直接返回 {kind:"retry"}，不再往下传；只有**换不了**的时候才把控制权交回内核做退避重试。
关掉它就回到旧行为（内核优先）。

### 2. 「这一轮已经死过的车道」必须记在会话里

旧代码换道时只排除**刚刚失败的那一条**，于是 A 失败 → 换到 B → B 失败 → 又换回 A，
一个步骤在两条死车道之间来回（session-e4a79c6d 第 4 回合在 qoder 上撞了 10 次）。
冷却账本管不了这件事：瞬时判决的冷却只有 30 秒，与「这一步刚栽过」是两回事。

现在 stepDeadLanes / turnDeadLanes 是换道唯一权威的排除面，并**在成功调用时自动放出来**
（一次成功就是这条车道活着的证据，否则一次抖动会把偏好车道钉到回合结束）。
预算之外再加 EXTRA_SWITCHES = 2：宁可多换两次，也不要在一个还有活车道的目录上把这一轮判死。

### 3. 换不了的时候要「等」，不要「报错」

候选全在冷却时旧代码 return next()，原始错误直接冒到界面——「本轮运行失败」。而账本里
明明写着每条车道什么时候回来。现在 lastResortPerStep（默认 1）允许本步骤挑**最早恢复**的
那条车道等到它回来再试一次（lastResortWaitMs，默认 20 秒；超过上限就直接放弃，因为
凭据/订阅型停车是小时级的，等它没有意义）。

### 4. 回合级自动续跑：替用户按下那次重试

回合以 reason.kind = "error" 收场时，调度器在回合边界用一条明确标注的 user 消息
（source.kind = "model-orchestrator-resume"）把这一轮续上，消息里写清中断原因与续跑次数。
三条边界：

- **只在回合边界做**，中途插话会把一次对话切成两半；
- **必须等 Agent 真的 idle 再 followup()**——落在仍在运行的 phase 上时内核只会把消息
  排进 next-turn 而**不唤醒驱动**，消息会一直躺着（「看起来续跑了其实没动」的形状）；
- **有上限**（autoResumeMax，默认 2，成功完成一个回合即归零），连续两次都救不回来就停下来
  通知用户，而不是把同一个死循环刷成几十条消息。续跑延迟与账本对齐：
  最早恢复的车道还要多久就等多久（上限 autoResumeWaitCapMs，默认 90 秒）。

不触发续跑的失败：ABORTED / INTERRUPTED / CANCELLED（用户或宿主自己停的）、
CONTEXT_WINDOW_EXCEEDED（同一上下文再跑一遍还是超）、INVALID_REQUEST（换渠道也一样不合法）。

### 新增/可调的配置

| 键 | 默认 | 说明 |
| --- | --- | --- |
| ownRetryBudget | true | 调度器而不是内核掌管同车道重试（关掉 = 内核优先，旧行为） |
| lastResortPerStep | 1 | 一个步骤内允许几次「等到最早恢复的车道」 |
| lastResortWaitMs | 20000 | 那次等待的时长上限 |
| autoResume | true | 回合以 error 收场后自动续跑 |
| autoResumeMax | 2 | 同一条失败链上的续跑次数上限 |
| autoResumeDelayMs | 1500 | 基础停顿（× 连击数） |
| autoResumeWaitCapMs | 90000 | 与账本对齐时的等待上限 |
| maxSwitchesPerStep | 5 | 由 3 提到 5（另有 2 次超额余量） |
| maxSwitchesPerTurn | 16 | 由 12 提到 16 |

应急开关（不用改 profile patch）：model_orchestrator 工具的 action: "set" 现在也接受
上面这七个新键，例如 {"action":"set","autoResume":false}。

## P0 缺陷批次：掩码判据、续跑定时器与配置面（2026-11-16，v2.12.0）

这一批全部来自对本机 35 天实盘账本与代码的评审，逐条都有构造用例锁住（`tools/smoke.mjs` 第 18 节）。

### 1. vision 回退会抹掉策略掩码（HIGH，路由正确性）

现象：请求带图片、而本机没有「有资格且支持图片」的车道时，早先的实现用 `all = inspectAll(true)`
整表重建评估面——那个构造器是对**原始 rows** 的 map，一次赋值把刚上好的两道掩码（家族停车 / 借入
闸门）全部丢掉：被本步骤停掉的家族与「本机还有活车道故留作兜底」的借入车道一起复活成合格候选。
仅改成「只重判合格条目」也不够：`inspectLane` 是纯判定，对刚被掩码判掉的条目一无所知，掩码会在
返回给调用方之前被重新抹掉（实测：`borrowUsable=false` 时借入车道复活并被选中）。

现在三类掩码一律**只记录判定**，改动只发生在一次渲染里，且语义分清：

- **策略掩码**（家族停车、借入闸门）是设计意图，**不**能被回退复活；
- **能力回退**（vision）只回答「这条车道愿不愿意在没有真视觉能力时顶一下」，允许被图片要求挡掉的
  本机车道顶上，并照旧吃 `fallbackPenalty`。

同时把两个互相读对方结果的掩码改成「先算资格、再渲染」：家族停车级联求解并以 **local 车道**为守卫
（借入车道从来不是「本机还有别的选择」的证据），互借闸门只数 local 候选——此前它们会被对方渲染出的
结果污染，出现「本机唯一视觉车道被停 → 借入车道反而参战」的反向行为。

### 2. 自动续跑定时器覆盖不清旧句柄（HIGH，会话正确性）

`scheduleAutoResume` 的等待窗口最长 90 秒；窗口内用户重试、或再次以 error 收场时都会再调度一次，
而旧实现只覆盖 `state.resumeTimer` 引用、不 `clearTimeout`，旧定时器照样到点执行：同一个会话被插入
第二条「模型调度自动续跑」消息，并重复消耗 `resumeChain` 预算。

### 3. 配置面不再说谎（三处）

| 键 | 旧行为 | 现在 |
| --- | --- | --- |
| `requestRepeatBlockMs` | 写 `0`（只换渠道不暂停）被 `Number(x) || fallback` 吞掉，仍停 30 分钟 | 显式 0 生效 |
| `concurrencyStaleMs` | 在 `MUTABLE_KEYS` 里、面板可改，但只在启动时读一次 | 惰性读取，改完立刻生效（地板 5 秒） |
| `maxSwitchesPerStep` | clamp 上限 10，填 20 静默变 12；超额余量硬编码 | 上限 30，超额余量成为配置键 `switchOverdraft` |

另外 `peerShare.token` 从面板/工具/HTTP 的展示面脱敏（它本是出借端点的凭据，此前随 `action=status`
原样进入工具结果与会话日志）；`MAX_INTEL` 与策略白名单收敛到 `policy-defaults` 单一事实来源。

### 回归用例

`node tools/smoke.mjs` 第 18 节：掩码不可被回退复活、能力回退确实生效、端点不可达时借入车道不参战、
本机真无候选时借入兜底仍在、`0` 生效且正例仍会停车、换道预算可配、策略白名单同源、`staleMs` 惰性生效。
## 数据从哪来（以及为什么更准）

| 数据 | 来源 | 用法 |
| --- | --- | --- |
| 模型清单、上下文窗口、模态、reasoning 档 | 内核 `llm.listProviders/listModels/resolveModelInfo` | 能力过滤、effort 选择 |
| 渠道账号、每账号每模型的限流解禁时间 | OFM 写的 `$DSH_HOME/channel-pack/state.json` | 渠道级可用性（只读） |
| 今日每渠道每模型的请求/错误/token/首字 | OFM 写的 `$DSH_HOME/channel-pack/token-ledger.json` | 第二优先的延迟证据 + 用量项 |
| 免费车道的逐模型可用性与探测延迟 | OFM 写的 `$DSH_HOME/our-free-model/availability.json` | 免费车道不可用/可用判定 |
| 免费车道今日逐模型统计 | OFM 写的 `$DSH_HOME/our-free-model/stats.json` | 免费车道用量 |
| 真实流量的首字、token、失败 | 本插件观测 `llm/stream` | 第一优先的延迟证据 + 健康账本 |
| 智力分、逐车道报告首字、标签 | 报告导入 / 随包 `priority-data.json` | **先验**，可信度收缩 |

关键点：

- **报告可以重新生成。** 工作区根的 `REPORT-模型测速与优先级.md` 是**生成物**：
  `node tools/_rebuild-report.mjs --write` 从 `src/priority-data.json` 重建它，
  `node tools/_merge-priority.mjs --write` 把更新的一份导入数据/实盘差集并进来，
  `node tools/build-data.mjs` 再反向生成数据集。三者互为校验（实测：13 车道 / 121 id / 79 家族 / 0 未解析）。
  2026-11-12 这份手写报告曾被截成 174 行片段并让 `smoke` 整组断言抛错，重建链就是那次事故的兜底。
- **报告只是先验。** 报告是别的机器、别的日期、benchmark 最大 effort 下测的。
  `quality` 会按「识别可信度 × 实测/估算」向 0.5 收缩：精确别名/规范表/改名折叠 0.9，
  模式猜测 0.7，报告没见过的 id 直接中性 0.5。它不会因为「报告没写」就被排除。
- **渠道改名不改家族。** 同一个模型换个 id 卖（`sn-deepseek-v4-1-flash` →
  `sn-deepseek-v4-1-flash-1017`、`opencode/deepseek-v4.1-flash`）仍归到同一个家族：
  识别会先试原样、再试去掉静态标记，最后**逐层折叠并回表验证**（构建号/日期戳、区域标记
  `-sg`、渠道命名空间 `xxx/`、渠道前缀 `sn-`、虚线版本号），只有折叠后**恰好命中已知模型**
  才采纳，所以猜错不产生任何后果，新后缀也不用改代码。见下节。
- **不再拿家族最快车道的首字当某条车道的首字。** 旧版会让一条 45 秒的车道继承另一条 1 秒车道的速度；
  现在只认**这条车道**的实测/账本/报告值，没有就承认「没有证据」。
- **渠道限流以渠道面板自己记录的为准。** 同一渠道多账号时，只有**所有启用账号**都被该模型限流才判不可用。
- **所有数据都在本机。** 不上传任何东西；渠道文件读取失败只是「没有信号」，路由照常工作。

### 模型识别：四道关卡

| 顺序 | 关卡 | 例子 | 可信度 |
| --- | --- | --- | --- |
| 1 | 原样命中别名 / 规范表 / 修正表 | `gmodel`、`z-ai/glm-5.3`、`deepseek-flash` | 1.0 |
| 2 | 折叠后**恰好命中**已知模型 | `sn-deepseek-v4-1-flash-1017`、`opencode/deepseek-v4.1-flash` | 0.85–0.95 |
| 3 | 命名约定模式 | `mimo-v2.6-flash-ultra`、`glm-5.3-flashx` | 0.65–0.7 |
| 4 | 认不出来 = 自己一个家族 | `brand-new-model-2099` | 0（中性分） |

第 2 关的折叠规则在 `src/families.js` 的 `FOLD_STEPS`（最多折三层，先试折叠次数最少的）：

| 折叠 | 去掉的东西 | 可信度 |
| --- | --- | --- |
| `snapshot-date` | `-2026-04-20` 这类日期戳 | 0.95 |
| `build-tag` | `-1017`、`-0731`、`-v2`、`-b3` 这类构建 / 修订号 | 0.95 |
| `region-tag` | `-sg`、`-us`、`-intl`、`-latest` 这类区域 / 渠道标记 | 0.95 |
| `namespace` | `opencode/`、`codearts/` 这类一层命名空间 | 0.95 |
| `channel-tag` | `sn-` 这类渠道自己的短前缀 | 0.85 |
| `version-dash` | 把 `v4-1` 折成 `v4.1` 这类虚线版本号 | 0.85 |

**为什么安全**：折叠只是「提议」，采纳的唯一条件是折叠后的 id 在别名表里**精确存在**。
所以 `brand-new-model-2099` 去掉 `-2099` 之后 `brand-new-model` 谁都对不上，直接退回身份家族，
不会把两个陌生模型混成一个；模型名本身以数字结尾的（`gpt-oss-20b`、`nemotron-3-super-120b-a12b`）
也照原样保留。

批处理端点是唯一例外：`:batch` / `:async` 永远保持自己的身份，绝不被折进交互式家族。

**屏蔽与放行跟着家族走。** 既然一个模型可以有多个 id，`deny: ["deepseek-v4.1-flash"]` 必须
把它所有拼写一起挡掉，否则换个后戳就是绕过自己的黑名单。规则：写家族名或任意一个已识别的 id
→ 整个家族被挡；写 `provider/model` → 只挡那一条车道。`denyProviders`（计费渠道用的那个）
本来就是渠道级，完全不经过模型识别。

## 界面

两个入口，同一份数据：

- **会话里**：输入框下方一条状态带（`conversation.composer.dock`，与「用量/余额看板」并排）；
- **新会话首屏**：新会话用的是另一个 composer 变体（`hero`），`composer.dock` 在那一屏**不渲染**——
  所以另注册了一个紧凑 chip 到 `conversation.hero.options`（工作区/预设那一行的右侧）。
  还没有任何请求时它显示**下一条消息将会用哪个模型**，点开是同一个面板的浮层。
- **官方模型列表最上方**：对话框右下角点开模型列表（两级菜单里选「模型」那一页），第一行就是
  **自动选择**，排在 `DeepSeek 账号` 上面。选中它 = 模型全部由调度决定；在这一页里点任何一个
  具体模型 = 你明确要那个模型，自动选择随即让位（面板「设置」里也有同一个开关，可以在不选模型的
  情况下关掉它）。
- **对话框右下角那个模型名**：官方 seat 的标签（`conversation.input.model.label`）由本插件接管。
  开启自动选择后那里显示的是**「自动选择」**——选择器里那个模型名这时已经不是实际被调用的模型；
  紧跟其后的推理档 chip 也一并隐藏（它同样只属于选择器）。关掉开关立刻恢复显示模型名，
  模型列表内部的每一行仍然显示各自的模型名，不受影响。

```
会话里：[模型调度 · 自动]  ● glm-5.3  可用  今日 12.4k  自动切换 2   ▾
首  屏：[● 模型调度 · 自动  glm-5.3 ▾]                    （点开是浮层面板）
右下角：[⌗ 自动选择 ▾]                                    （开启自动选择时，官方 seat 被改写）
```

展开后的面板按标签页分（一屏之内，不再是一条几十行的长栏）。2026-11-04 起新增「巡检」页签与概览巡检卡：

- **头行**：模式（自动 / 偏好 / 手动 / 关闭）、当前策略、刷新；
- **概览**：当前模型卡（家族、真实渠道、推理档、请求数、自动切换、失败原因与倒计时）、
  偏好卡（当前偏好 + 可用渠道数 +「设为偏好」+「浏览全部模型…」）、目录卡、**巡检卡**（开关状态、
  上次结果通过数、一键跳到巡检页），以及**策略排名前 4** 的模型组；
- **模型**：全部模型组（★ 设为偏好、可用渠道/总渠道、最佳渠道、智力、得分）；
- **渠道**：当前模型的渠道表（渠道、状态、得分、首字、今日 token）；
- **巡检**：定时渠道巡检的完整面 —— 开关、间隔（1/3/7/14 天）、**立即跑一轮**按钮、是否也探借入车道、
  上次/下次时间与耗时、通过/失败/跳过计数、**失败原因聚合计数**（如「14× 冷却中」）、
  每条车道的判决表（渠道、结果、耗时、原因原文）；Host 是旧版本时这一页显示「未提供巡检数据」，
  面板其余部分照常工作。
- **记录**：最近切换（时间、从哪到哪、为什么）；
- **设置**：策略、偏好模型（下拉列出**全部**模型，不截断）与备用模式、推理档、单轮 token 预算、
  渠道数据接入状态、**首轮接管**开关、**自动选择**开关；
- 偏好暂停时，概览顶部出现横幅：原因 + 「重试偏好」。

偏好模型有两个入口：模型组表里点 ★ 直接设；或点「浏览全部模型…」打开**专用选择器**——
搜索框 + **全量**模型组列表（每行给出可用渠道/总渠道、最佳渠道、智力、视觉、上下文窗口），
点一行即设为偏好，另有「不锁定偏好（回到自动调度）」。下拉与列表都由 `/api/model-orchestrator/families`
提供：它是**不截断**的全量清单，只在这个界面打开时按需拉取，不跟着 10 秒轮询走。

面板只读 `/api/model-orchestrator/summary`、写 `/api/model-orchestrator/config`；巡检页签另走
`/api/model-orchestrator/probe`（GET 只读状态，POST `{action:'run-now'}` 跑一轮——读和写分开成独立路由，
因为跑一轮会真实消耗额度，不能被一次误发的配置写入顺带触发）。
所有路由都走宿主自己的鉴权闸门（`ctx.connection`），未登录的 loopback 调用者拿到 401。
`summary` 里的巡检块带条数上限（60 条，超出的只报 `truncated`），所以 10 秒轮询不会因为
一轮几十条的巡检结果悄悄变贵；完整明细走工具 `action=probe`。

## 配置

写在 profile 的 `cordis.patch.yml`（优先级最高），或在面板里改（存到 `$DSH_HOME/model-orchestrator/overrides.json`）。
补丁层里显式写过的键会盖过面板。

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关。 |
| `mode` | `auto` | `auto` / `prefer` / `manual` / `off`。 |
| `preferModel` / `preferProvider` | `''` | 偏好模型（家族 id、模型 id 或 `provider/model`）与可选渠道限制。 |
| `preferFallback` | `auto` | 偏好不可用时的模式：`auto` / `manual` / `off`。 |
| `preferNotify` | `true` | 暂停/恢复时发桌面通知。 |
| `preferAutoResume` | `true` | 渠道恢复后自动恢复偏好。 |
| `preferFollowSelection` | `true` | 选择器改选时同步改偏好模型。 |
| `strategy` | `balanced` | `quality` / `balanced` / `economy` / `speed`。 |
| `deny` / `allow` | `[]` | 额外屏蔽 / 放行的模型（家族名、任意一个 id，或 `provider/model` 精确到单条车道）。写家族名或某个 id 会覆盖这个名字的所有拼写；写 `lane/model` 只作用于那一条车道。 |
| `denyProviders` | `[]` | 整条渠道排除（按渠道 id，与模型识别无关；计费渠道常驻这里）。 |
| `maxSwitchesPerStep` / `maxSwitchesPerTurn` | `5` / `16` | 同一步/同一轮最多自动切几次。 |
| `switchOverdraft` | `2` | 预算之外的「宁可换也不要死」余量；实际预算 = maxSwitchesPerStep + 这个值（2026-11-16 由硬编码常量变成配置键）。 |
| `requestRepeatThreshold` | `2` | 同一渠道在窗口内连续拒绝几次后暂停该模型（1–10）。 |
| `requestRepeatWindowMs` | `600000` | 上面那个「连续」的时间窗口。 |
| `requestRepeatBlockMs` | `1800000` | 连续被拒后暂停多久（**0 = 只换渠道不暂停**；2026-11-16 修掉了「写 0 仍按 30 分钟停车」的 `||` 吞值）。 |
| `proactiveSwitch` | `true` | 冷却中的渠道直接跳过，而不是等它。 |
| `escalateOnFailure` | `true` | 失败后优先换到智力不低于失败模型的模型。 |
| `turnTokenBudget` | `0` | 单轮输出 token 预算，超出后切省 token 档；0 关闭。 |
| `longContextThreshold` | `120000` | 超过这个 prompt 规模就只考虑长上下文模型。 |
| `latencyGateMs` | `10000` | 首字达到这个值时速度项为 0.5；0 关闭。 |
| `anchorBonus` | `0.04` | 保持当前渠道的加分（只影响渠道层，不参与模型比较）。 |
| `switchMargin` / `laneSwitchMargin` | `0.04` / `0.05` | 换模型 / 换渠道的粘滞阈值。 |
| `spreadConcurrency` | `true` | **并发分散**：按「此刻正在飞的调用数」给车道扣分，多个会话不会一起堆在同一条最好的渠道上（见下节）。关掉退回纯历史排名。 |
| `concurrencySoftCap` | `2` | 在飞的调用数达到几个时扣满（1–16）。 |
| `concurrencyWeight` | `0.18` | 并发扣分的上限（0–0.3）。必须大于 `laneSwitchMargin`，否则「知道它忙」也换不动。 |
| `concurrencyStaleMs` | `900000` | 一个在飞租约超过这么久就停止计数（流没关掉的兜底）。**运行期可改，改完立刻生效**（2026-11-16 之前只在启动时读一次；地板 5 秒，与 config 的 clamp 下限一致）。 |
| `failureBurstWindowMs` | `5000` | 同一车道、同一失败类型在这个窗口内的多次上报算**一次**事件：只记一次 strike，冷却不往后滑。 |
| `userChoiceTtlMs` | `1800000` | 手动选择器改动被尊重的时长（自动模式，翻倍阈值）。 |
| `routeFirstTurn` | `true` | 首轮接管：新会话第一条消息就按调度结果调用模型。关掉后首轮先跑选择器里的模型，第二步起才由路由器接。 |
| `autoSelect` | `false` | 自动选择：模型完全由调度决定，官方模型选择器只作展示（选它不会改变实际调用）。`manual` 在这个开关下按 `auto` 处理。 |
| `routeSubagents` | `false` | 是否也路由子代理会话（默认让子代理自己的模型选择生效）。 |
| `reasoningEffort` | `auto` | `auto`（按策略）/ `preserve`（能保留就保留）/ 具体 effort。 |
| `channelData` / `freeModelData` | `true` | 是否读取渠道面板账本 / 免费车道探测。 |
| `catalogRefreshMs` / `channelDataRefreshMs` | `120000` / `30000` | 模型清单 / 渠道数据的刷新间隔。 |
| `modelInfoTtlMs` | `21600000` | 模型元数据缓存时长。 |
| `usageUnitTokens` | `2000000` | 用量项的参考规模。 |
| `reportPath` | `''` | 启动时自动导入这份报告。 |
| `probeEnabled` | `true` | 定时渠道巡检开关。 |
| `probeEveryDays` | `3` | 巡检间隔（天）。被 `probeIntervalMs` 覆盖。 |
| `probeIntervalMs` | `0` | 巡检间隔（毫秒）。`>0` 时优先于 `probeEveryDays`。 |
| `probeTimeoutMs` | `20000` | 单条车道的探测超时。 |
| `probeConcurrency` | `2` | 一轮内同时探测几条车道。 |
| `probeFirstDelayMs` | `600000` | 首轮延迟（10 分钟），避开启动时的会话。 |

### 定时渠道巡检（`probe`）

免费车道会「静默死亡」：某个渠道 402 额度耗尽、某个免费层永久限流、某个模型悄悄下架。
这些只有**被选中并失败一次**之后健康账本才会知道——若很久没人选它，面板上的「可用」就是假的。

`probe` 按间隔把所有未 deny 的车道主动探一遍，把结果写回同一本账（`health.json`）：

- **默认三天一次**。探活要花额度，太勤等于替用户烧钱；太疏账本又失真。
- **冷却未到期的车道直接跳过**：它本来就不会被选中，探了只是白烧额度。
- **探活请求带 `purpose='probe'`**，不计入会话的 `turnTokenBudget`。
- **单条独立超时 + 并发上限**：一条挂死不拖垮整轮。
- 关掉：`probeEnabled: false`；立即跑一轮：`model_orchestrator action=probe probeMode=run-now`，
  或面板「巡检」页签里的「立即跑一轮」按钮（两者走同一份实现）。

### 面板上的巡检页签

2026-11-04 加：在此之前 probe 只有工具入口，面板里**找不到**它（这也是它当时"像没做完"的原因）。
现在展开面板即可看到「巡检」页签：

| 控件 | 作用 |
| --- | --- |
| 巡检开关 | 写 `probeEnabled`。关掉后定时器停排，但已排队的一轮仍会跑完。 |
| 间隔下拉 | 1 / 3 / 7 / 14 天，写 `probeEveryDays`；下一轮按新值重排（不用重启）。 |
| 立即跑一轮 | POST `/probe {action:'run-now'}`，真发请求、真花额度；跑完立刻重读 summary。 |
| 也探借入车道 | 写 `probeBorrowed`（默认关）。 |
| 判决表 | 上一轮每条车道的渠道 / 结果 / 耗时 / 原因原文。 |
| 失败归因 | 把失败原因按原文聚合计数，一眼看出「是整条渠道挂了还是某个模型挂了」。 |

概览页另有一张巡检卡：开关状态 + 上次通过数 + 跳到页签的按钮 —— 不打开页签也能看到「该做的事做没做」。

**旧键兼容**：`pinProvider`/`pinModel` 会被折叠成 `preferModel`/`preferProvider`，并把 `auto` 改为 `prefer`。

## 它是怎么接进内核的

- **决策点：`system-prompt/assemble`（`prepend: true`）。** 内核在组装时快照本步模型；插件在快照前写入选择。
- **自动选择（`autoSelect`）。** 锚点里不再有选择器、也不再有 `requestHeader`：只保留本插件自己写过的路由
  （所以同一轮内粘滞照常）。打开时立刻按当前策略重算一次并写回 selection，模型座位当场变化；`manual` 与它
  冲突，打开时 `manual` 落到 `auto`。**在官方模型列表里点了某个具体模型 = 一条明确指令**：退出自动选择、
  采纳这次选择（列表首行的「自动选择」就是重新接管），并在决策日志里留一条 `auto-select-off`。
- **列表首行是注入的，不是 slot。** 官方模型选择器（`client-ui-model-selection`）独占座位与菜单，只开放一个
  `conversation.input.model.label` 子槽；替换座位等于影子掉整个官方选择器（搜索、推理档、子代理门禁、键盘导航）。
  所以那一行由 `MutationObserver` 在模型页出现时插进渲染出来的列表里，React 把它丢掉时会补回去。
- **首轮接管（`routeFirstTurn`）。** 会话还没有 `requestHeader`、本插件也还没写过路由时，选择器里的模型只算
  「上次用过的那个」，不是本轮指令：锚点直接给 `null`（不标 `userChoice`），`selectRoute` 从全表选最优，
  再把结果写进 `model/selection`，于是选择器跟着路由器走而不是反过来。会话建立过程中内核自己写的
  初始 selection 事件在这里一并丢掉，否则下一步会立刻锚回它。
- **写选择：`sessionController.selectForNextRequest(agent, selection)`。** 它同时追加 `model/selection`
  事件并更新选择对象，这是浏览器选择器、会话日志和面板保持一致的唯一正确路径。
- **请求兜底：`agent/request`。** 在 `next()` 之后再按 `state.applied` 覆盖一次 `provider/model/effort`，
  保证真正发出去的请求就是路由器选的那条。
- **同一步故障转移：`agent/request-error`。** 返回 `{kind:'retry'}` 让内核在同一 step 重新解析配置。
- **观测：`llm/stream`。** 只记录抛出的异常；带内 `finish.error` 交给 `agent/request-error`，
  避免一次失败记两次（非 agent 循环的调用例外，它们没有 request-error）。
- **同步：`llm/adapters-updated` + 自适应定时器。** 新登录的渠道账号会自动出现；刷新间隔改了不用重启。

## 已知边界

- **只路由 agent 的模型请求。** 其它直接调用 `ctx.llm.stream` 的代码不经过本插件（但仍会被观测用量）。
- **剩余额度不可知。** 免费渠道的上游不告诉你余额；面板显示的是状态、冷却、实测首字和本插件统计的用量。
- **报告是快照。** 报告没有的模型按中性先验处理；跨版本 AA 分数不可比。
- **家族识别仍可能有误。** 精确别名/规范表可信；改名折叠 0.85–0.95，模式匹配只有 0.7；
  识别错了会把不同模型当成同一个，或者把同一条路线的两个 id 合成一组（合并只影响打分与选择器
  的显示，不影响真实调用走哪个 id）。
- **对 OFM 是单向适配，不是合作，也不是官方关联。** 本插件只读它写的四个 JSON：不改它、不向它提需求、
  也不向它的仓库提交适配改动；OFM 作者既未参与本插件的开发，也未为它背书。
- **渠道账本读的是 [dsh-our-free-model](https://github.com/Ebony-Vinyl/dsh-our-free-model) 的私有文件格式。**
  那四个 JSON 是 OFM 的内部状态，没有版本承诺；文件缺失或结构变化时自动退化为「没有信号」，不会阻断路由。
  见 [与 dsh-our-free-model 的关系](#与-dsh-our-free-model-的关系)。
- **偏好模式的「全部渠道不可用」是全局判断。** 一次请求的图片/窗口限制只会临时改选，不会暂停偏好。
- **注入的那一行不参与官方菜单的键盘导航。** 官方 `↑/↓` 只在它自己的条目里走；这一行用 Tab 可达。
  官方若改了菜单结构，最坏情况是这一行不出现，不会影响官方选择器本身。
- **自动选择是全局开关，不是每会话一份。** 它决定「选择器还算不算指令」，属于同一个人的使用习惯；
  会话级会是另一种产品（同一份会话列表里有的会话听调度、有的听选择器），所以没做。
- **官方 seat 标签是「接管」而不是「叠加」。** `conversation.input.model.label` 是 `single` 槽，
  DSH 随发行版带的 1017 发布标签（`@deepseek-ai/dsh-client-ui-deepseek-model-label-1017`）也占着它，
  本插件按框架自己的 shadow 规则用 `priority: -1` 取胜——代价是那个给 DeepSeek 官方 Flash 加「1017」
  徽标的装饰不再显示（只影响该徽标，选择器与模型列表本身不受影响）。隐藏推理档 chip 是 DOM 层的小手术，
  指向 seat 自己的标签行；官方若改了触发按钮结构，最坏情况是那枚 chip 不被隐藏，不会报错。
- **首轮接管只作用于 auto 模式的首个组装。** `prefer` 按偏好模型走，`manual` 按选择器走；
  `off` 不介入。关掉 `routeFirstTurn` 就回到「首轮先跑选择器里的模型」。
  新会话页的 chip 展示的是**预计**路由（那一刻还不知道这条消息要不要图片或长上下文），
  真正发出去的那条由 `system-prompt/assemble` 现场算。
- **切换会改变模型看到的上下文。** 换 provider 时内核会丢掉适配器私有的 replay 信封（文本与工具历史保留），
  并追加一条持久提示告知模型发生过切换——这是内核设计好的行为。
